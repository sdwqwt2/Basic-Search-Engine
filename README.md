# Avito Candidate Generation

Решение этапа кандидатогенерации для поиска услуг Авито: по короткому поисковому
запросу отобрать до 50 объявлений-кандидатов из корпуса (189 212 объявлений).
Метрика — Recall@50.

**Результат на лидерборде: Recall@50 = 0.350** (гибридный поиск, `alpha=0.5`).

## Подход

Гибридный поиск: лексический (BM25) + семантический (bi-encoder), слитые через RRF,
поверх фильтра по категории.

1. **Фильтр по категории.** По EDA `search_category` почти неинформативен (два значения,
   `0` и `114`, при 47 значениях `item_category_id`), поэтому основной сигнал —
   маппинг **текст запроса → категория объявления**, выученный на `train.parquet`:
   у >99.99% запросов одна категория покрывает ≥80% выборов пользователей.
   `search_category` используется, только если он валиден и встречается среди
   категорий объявлений. Для запросов, которых нет в train, поиск идёт по всему корпусу.
   По умолчанию допускаются 2 самые частые категории запроса (`--top-n-categories 2`).

2. **Два независимых поиска по одному общему индексу на весь корпус:**
    - **BM25** (`rank_bm25`, BM25Okapi) по полному тексту `title + params + description`.
    - **Bi-encoder** `intfloat/multilingual-e5-base` + FAISS (`IndexFlatIP` по
      нормализованным эмбеддингам, то есть cosine). Текст объявления: title + params +
      обрезанное description; `max_seq_length=192` токенов; префиксы E5
      `query:` / `passage:`.
      Фильтр по категории применяется на этапе поиска: маскирование скоров в BM25 и
      `faiss.IDSelectorArray` в dense, без пересборки индексов под категорию.
      Из каждого метода берётся top-100 кандидатов.

3. **Слияние — Reciprocal Rank Fusion** с весом `alpha`:

```
   score(item) = alpha * 1/(k + rank_bm25) + (1 - alpha) * 1/(k + rank_dense),  k = 60
```

Отсутствие объявления в одном из списков даёт нулевой вклад от этого списка.
RRF работает по рангам, а не по сырым скорам, поэтому не требует нормализации
скоров разной природы (BM25 и cosine). В итоговом решении `alpha = 0.5`
(значение по умолчанию, отдельный подбор не проводился, см. «Ограничения»).

Так как Recall@50 не зависит от порядка внутри топ-50, ранжирование не оптимизировалось:
задача решения — чтобы релевантные объявления попали в 50 кандидатов.

## Используемые open-source компоненты

- `intfloat/multilingual-e5-base` — bi-encoder (загружается один раз с HuggingFace Hub
  и кешируется, инференс полностью локальный, без внешних API).
- `sentence-transformers`, `transformers`, `torch` — энкодинг.
- `faiss-cpu` — векторный индекс.
- `rank_bm25` — BM25.
- `pandas`, `pyarrow`, `numpy`, `scikit-learn`, `tqdm`.

## Установка

Python 3.11.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e ".[notebooks]"   # с jupyter/matplotlib для ноутбуков
# или: pip install -e .         # только для запуска скриптов
```

Положи данные в `data/raw/`: `train.parquet`, `benchmark_queries.parquet`,
`benchmark_items.parquet`.

## Воспроизведение

### 1. Построение индексов

```bash
python -m avito_retrieval.build_index --max-seq-length 192 --batch-size 128 --top-n-categories 2
```

Индексы строятся один раз на весь корпус и сохраняются в `data/indices/`.
Устройство выбирается автоматически: CUDA → MPS → CPU.
На MacBook с Apple Silicon (MPS) построение заняло порядка 2 часов. <!-- ПРОВЕРЬ: подставь фактическое время -->

### 2. Финальный прогон

```bash
python -m avito_retrieval.main --alpha 0.5 --top-n-categories 2 --max-seq-length 192
```

Скрипт загружает индексы (или строит их при `--rebuild-index`), обрабатывает все 2452
запроса, проверяет формат ответа (≤50 уникальных `item_id` на запрос, все `item_id` есть
в корпусе, покрыты все `query_id`, нет дублей) и пишет `answer_hybrid.csv`.
Обработка запросов заняла около 2 часов (7307 с) на том же MacBook.

`--max-seq-length` при загрузке индексов должен совпадать со значением, с которым индексы
строились: он влияет на энкодинг запросов.

### Параметры main.py

| Флаг                 | По умолчанию                    | Описание                                               |
|----------------------|---------------------------------|--------------------------------------------------------|
| `--alpha`            | 0.5                             | Вес BM25 в RRF (1.0 — только BM25, 0.0 — только dense) |
| `--top-n-categories` | 2                               | Сколько категорий на запрос допускает фильтр           |
| `--top-k-each`       | 100                             | Кандидатов из каждого метода до слияния                |
| `--final-top-k`      | 50                              | Итоговое число кандидатов                              |
| `--max-seq-length`   | 192                             | Макс. длина в токенах для bi-encoder                   |
| `--model-name`       | `intfloat/multilingual-e5-base` | Модель bi-encoder                                      |
| `--rebuild-index`    | выкл.                           | Пересобрать индексы вместо загрузки                    |
| `--index-dir`        | `data/indices`                  | Каталог индексов                                       |
| `--output-path`      | `answer_hybrid.csv`             | Куда сохранить результат                               |

Random seed фиксирован (`config.SEED = 42`). Небольшая недетерминированность на
GPU/MPS в энкодинге теоретически возможна.

## Ограничения

### Временные

Решение делалось в рамках срока около 1-2 дней на задачу, где для осмысленного сравнения
нужно запускать эксперименты на нескольких архитектурах (разные bi-encoder, sparse-модели,
реранкеры). Времени хватило на один сквозной гибридный пайплайн и один бейзлайн.
Из-за этого:

- **`alpha` не подбирался**: использовано значение по умолчанию 0.5, поэтому оно почти
  наверняка не оптимально. Так же не тюнились `top_n_categories`, `top_k_each` и
  параметр `k` в RRF.
- **Модели не сравнивались**: использован один bi-encoder (`multilingual-e5-base`).
  Кандидаты из `config.BIENCODER_CANDIDATES` (e5-small, multilingual MiniLM, sbert_large_nlu_ru)
  не были прогнаны.
- **Не пробовались** SPLADE, ColBERT и реранкинг cross-encoder'ом. Отметим, что реранкинг
  внутри топ-50 на Recall@50 не влияет и имел бы смысл только для отбора из большего пула.

### Вычислительные

Все запуски выполнялись на одном ноутбуке (MacBook с Apple Silicon, MPS, `faiss-cpu`,
без CUDA). Это определило дизайн решения:

- Энкодинг корпуса (189 212 объявлений) — самая дорогая операция: порядка 3.5 часа.
  По замерам стоимость почти линейна по длине последовательности (на подвыборке из 3000
  текстов: 40.9 с при 128 токенах, 94.1 с при 256, 161.8 с при 512), поэтому
  `max_seq_length` ограничен 192, а `description` обрезается до энкодинга. По EDA p50 длины
  полного текста объявления — 557 токенов, p95 — 1645, то есть большая часть описания
  в dense-представление не попадает (title и params стоят в начале текста и
  сохраняются). Длины 128/256/512 сравнивались только по времени; влияние на
  Recall@50 не измерялось.
- Индексы строятся один раз и сохраняются; каждый эксперимент с моделью или длиной
  требует нового многочасового энкодинга. Это сильно ограничило число итераций.
- Поиск идёт по одному запросу за раз: `rank_bm25` каждый раз пересчитывает скоры по всему
  корпусу, а для dense строится маска категории. Это дало ~3 секунды на запрос
  (7307 с на 2452 запроса). Быстрее было бы `bm25s` и батчевый поиск на устройстве.
- Количество попыток на лидерборде ограничено семью; ни абляции по отдельным компонентам,
  ни подбор гиперпараметров на них не проводились.

### Методологические

- Разметка есть только у `train.parquet`, а у бенчмарка её нет, поэтому валидацию пришлось бы
  строить из train (корпус меньше и «легче» реального), и абсолютные значения на ней не
  предсказывали бы лидерборд.
- Фильтр по категории — эвристика на основе train: для запросов, которых там нет, он
  не срабатывает. Потери полноты из-за самого фильтра (релевантное объявление вне
  допустимых категорий) не измерялись.

### Что не использовано, но выглядело перспективным

- **Локация.** В train `search_location_id` совпадает с `item_location_id` в 83.1%
  пар, а в среднем в локации запроса находится лишь 2.49% корпуса, то есть фильтр
  или буст по локации мог бы сильно сузить поиск. Локации иерархичны (одинаковые
  расхождения повторяются, напр. `107620 → 637640`), поэтому нужен выученный маппинг, а не равенство.
- **Дообучение bi-encoder** на 497k парах «запрос → выбранное объявление»
  (контрастивный лосс с in-batch негативами): у готового e5 нет сигнала о том, что именно
  выбирают пользователи.
- **Признаки популярности** (рейтинг, число отзывов, цена) и параметры фильтров поиска
  как приоритет или фильтр по `item_infm_params_text`.
- **Более быстрая реализация поиска** (`bm25s`, батчевый матричный поиск на устройстве),
  которая сделала бы эксперименты в разы дешевле.
